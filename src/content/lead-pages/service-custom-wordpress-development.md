## Build beyond a standard website page

Some organizations need more than a standard WordPress website: a custom interaction, an integration with an existing business system, or a feature that does not fit the site’s current tools. Custom development begins with understanding the user need, the site’s current setup, and the systems the feature must work with.

Ark’s standard website design scope does not automatically include custom programming, e-commerce, or new features. Those needs are reviewed and quoted separately. This page is an invitation to discuss a possible scope, not a promise that every feature or integration is supported.

## Start with the problem and constraints

Describe what a visitor or staff member needs to accomplish, what happens today, and which systems are involved. Share relevant documentation for the current WordPress theme, plugins, hosting environment, and external API or platform. Do not send credentials in an open message. If access is needed for assessment, we’ll coordinate a secure method and agree on its scope.

We’ll consider whether the requirement can be met with existing WordPress capabilities or whether custom code is appropriate. The assessment should account for security, maintenance, compatibility, data handling, and who will own future updates. Sometimes the best recommendation is a simpler workflow or a third-party service instead of custom development.

## Define a bounded project

Before development, we confirm the desired behavior, user roles, data exchanged, error states, integrations, testing needs, and acceptance criteria. We also identify dependencies, such as API access, vendor approval, hosting permissions, or sample data. If the scope is not clear enough to estimate, a discovery step may be needed first.

Any proposal should state deliverables and exclusions. For example, ongoing support, third-party subscription costs, data cleanup, or content migration may be separate from the initial build. We’ll clarify how changes to the requirement are reviewed and quoted.

## Consider ongoing ownership

Custom functionality needs a clear ownership and maintenance plan. Document where the code lives, how it is tested, what credentials or API keys it uses, and who will update it when external services change. WordPress’s maintenance guidance recommends keeping the site’s components and backups in a regular care routine ([WordPress site maintenance](https://wordpress.org/documentation/article/wordpress-site-maintenance/)). Any ongoing support must be separately scoped and agreed.

We also discuss what happens if the feature fails, how staff can report issues, and whether routine care covers any support. No integration can be guaranteed to remain compatible if a third-party system changes without notice; the support and review plan should reflect that dependency.

### Frequently asked questions

**Can you quote from an idea alone?** A useful estimate usually needs the user flow, platform details, integrations, and acceptance criteria. If those are unknown, the first step may be discovery.

**Are third-party costs included?** Not by default. Any subscriptions, APIs, or licenses are identified separately in the agreed scope.
